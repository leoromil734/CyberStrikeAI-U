# 并发任务下的接口性能观测

本文描述本地代码中的性能改进和验证方法。修改代码不会部署或重启服务；上线需另行批准。

## 事件流协议

- 每个流由 `streamId` 标识，`streamSeq` 从 1 开始递增；`message` 是纯增量，不应再做累计片段猜测。
- 第一帧、距上次快照至少 2 秒或 128 帧时携带 `data.accumulated`；流结束时再发送一个空 message 的最终 delta，带 `streamFinal=true` 与完整快照。
- 客户端丢帧后暂停拼接，等下一个快照恢复；重复序号忽略。没有 `streamSeq` 的历史/旧格式继续按原逻辑处理。
- 订阅队列拥塞时丢弃最旧帧，优先保留最新状态。事件流不是可靠消息队列，最终持久化记录仍为历史查询的依据。
- 前端和后端应配套发布，模板已更新 chat/monitor/router 的静态资源版本。部署后仍应刷新已打开的页面，避免旧页面继续消费新协议。
- 恢复时先建立展示订阅再加载最新历史；历史等待至多 5 秒、256 帧或约 1 MiB，达到上限时取消历史请求并转为实时展示，不取消后台任务。

## 过程详情分页

`GET /api/messages/:id/process-details?latest=1&limit=50&include_summary=false`

- `latest=1` 直接返回最新页，避免恢复时从第 0 页顺序加载所有记录。
- `include_summary=false` 跳过读取全部工具 payload 的摘要计算；省略 `toolExecutions` 字段。
- 为旧调用方保留默认包含摘要的行为。`summary=1` 单独按需请求，前端同一详情容器复用一次摘要请求以恢复跨页工具终态，后续翻页不重复查询。
- 响应 `nextOffset` 按原始数据库行数前进，避免显示去重后反复加载同一页。
- `anchorId` 优先于 `latest`。旧 `limit/offset`、全量导出 `full=1` 保持兼容。

## 慢请求日志

- 普通请求耗时达到 1 秒，输出 `HTTP slow request` 警告。
- SSE/升级连接单独处理：连接存活时间不作为慢请求判断；首次实际写入超过 1 秒才记录慢请求。正常流结束记录 `HTTP stream completed`。
- 字段：`request_id`、路由模板 `route`、方法、状态码、`duration_ms`、`first_write_ms`、响应字节数、是否流式及主数据库池快照。
- 响应头包含服务端生成的 `X-Request-ID`，用于浏览器与日志关联。首次写入时间不是浏览器 TTFB，不包含客户端网络/代理排队。
- 新增观测日志不记录查询字符串、原始资源 ID、Authorization 或请求正文。原有访问日志策略不受此调整影响。
- 日志在请求结束时记录，尚未完成的流不能仅凭该日志判断是否卡住。

## 数据库连接池

- `/api/monitor/stats` 在全局数据权限下增加 `databasePool`：连接上限、已打开、使用中、空闲、累计等待次数和等待毫秒数及连接回收次数。
- 字段反映应用的 `database/sql` 连接池，而非 PostgreSQL 整台服务的连接总数；等待值从当前进程启动开始累计。
- 每个数据库连接池（包括独立知识库）每 30 秒采样，发生新增连接等待时输出 `Database connection pool wait detected`，包含采样期间的等待次数/时间增量。
- 等待时间是多个调用的合计，可能超过 30 秒，不能直接当作一个请求的耗时。
- 无新增等待时只输出 Debug 采样日志；数据库关闭或重新配置时随原池停止采样，避免遗留定时协程。

## 上线后只读验证建议

1. 对比同一类任务和相近历史长度下的普通接口耗时与浏览器 Queueing/Stalled/TTFB，而不只看任务数。
2. 连续切换 A → B → A，会话展示订阅应始终只保留当前一个；取消展示订阅不能取消后台任务。
3. 运行中会话首次打开应直接请求最新页，不出现从 offset=0 开始的数十次串行恢复请求。
4. 观察完整事件流累计传输字节数，和相近长度任务的旧版本比较；模拟测试节省比例不等于生产实际收益。
5. 如仍慢，关联 `X-Request-ID`、慢请求日志、连接池等待增量和 PostgreSQL 等待事件，继续定位具体等待位置。
