# 客服/帮助台 MFA 重置与社会工程

> 一条正在被规模化使用的路径：**不攻击技术，攻击流程**。攻击者冒充员工联系 IT 帮助台，说服其重置 MFA 或改绑手机号，然后以合法身份登录。

## 一、攻击流程

1. **侦察**：从 LinkedIn、数据泄漏、公开仓库、社交平台收集目标的姓名、工号、部门、经理、常用设备、"生日/宠物"等知识型验证信息。
2. **接触**：电话/Teams/在线客服；常用话术是"手机丢了/出差途中/换新设备"。
3. **通过验证**：以收集到的 PII 回答知识型问题（KBA），或利用客服流程只有 1-2 个问题的弱点；也有可能配合**语音克隆**或**改号（Caller ID 伪造）**。
4. **重置**：客服删除既有 MFA 方式 → 攻击者用自己的设备重新注册 TOTP/passkey（**"强制重置"变体**：后续登录对受害者来说看起来完全正常）。
5. **使用**：立即通过 SSO 门户进入，并在 60 分钟内做侦查与横向（真实案例中速度极快）。

## 二、为什么难防

- 认证日志里显示的是**合法的用户与设备**，只是"新注册了一个 MFA 方法"。
- 无恶意软件，全部使用内置工具与合法 RMM。
- 受害者本人在重置完成前往往不知情。

## 三、常见变体

| 变体 | 说明 |
|---|---|
| MFA 重置 | 删除旧方式、注册新的（本文） |
| SIM Swap | 通过运营商把号码转移，从而接收 SMS/电话 OTP |
| 改绑邮箱/恢复邮箱 | 通过客服改绑到攻击者控制的邮箱 |
| 密码重置 + 绕过 MFA | 利用"忘记密码"与"新设备"的组合路径 |
| MFA Fatigue（推送轰炸） | 配合弱口令与重复推送，等待用户误点（**需授权与用户配合，风险高**） |
| 设备码钓鱼 | 让用户自己在真实页面批准（见 `Device-Code-Phishing.md`） |

## 四、评估方法（授权范围）

红队评估通常用"**流程验证**"替代真实社工：

1. **桌面推演/流程审计**：向 IT/客服索取身份核验 SOP，检查：
   - 重置 MFA 是否属于**特权操作**并需要升级审批？
   - 是否要求**回拨已登记号码**（而非用户提供的新号码）？
   - 是否有视频/工单/主管联签？
2. **受控演练**：与客户约定"内部红队打一个预先知道的电话"，记录：
   - 客服提了哪些验证问题、是否试图回拨、
   - 是否用现有 MFA 通道二次确认。
3. **技术侧检查**：
   - 重置流程是否触发告警（ITDR/UEBA）？
   - 新 MFA 注册后是否自动撤销既有会话？
   - 是否有"新 MFA 注册后 24 小时内高危操作二次验证"？

任何涉及真实员工的社工测试都需要**书面授权 + 明确的豁免名单**（如 CEO、财务），并预设事件升级路径。

## 五、验证（最小证据）

- 流程证据：SOP 文本、客服对话记录（脱敏）、演练脚本与观察记录。
- 技术证据：MFA 方法变更的审计日志（谁、何时、从哪）、会话未撤销的证据（旧会话在 MFA 变更后仍可用）。
- 影响：若演练真的重置成功，记录"可随后登录并访问的资源类型"，不访问真实敏感数据。

## 六、常见误报

- 客服拒绝重置（**这是正向结论**，应记录为控制有效）。
- 只获取到信息但未完成重置。
- 用户在演练中被提前告知，与实际情形不同。

## 七、修复要点

- **把身份恢复当作特权操作**：升级审批 + 回拨已登记号码 + 视频核验。
- 全部客服通话录音并留档；工单必须包含核验过程。
- **新 MFA 注册 = 高危事件**：通知用户（多通道）、要求 24 小时内二次验证、并撤销该账号的所有既有会话。
- 使用抗钓鱼 MFA（passkey）并在重置时要求**原设备确认**或临近工位核验。
- ITDR/UEBA 规则：`MFA 方法变更 + 新设备/新地理登录 + 短时间内权限提升` 的组合告警。
- 密码/MFA 变更后强制重新认证全部会话（含 API 令牌与 OAuth 授权）。
