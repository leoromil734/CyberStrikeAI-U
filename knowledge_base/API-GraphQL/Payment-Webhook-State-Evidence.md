# 支付 Webhook 签名、事件归属与状态证据

## 适用与触发

已确认支付/权益回调入口、提供商方案和处理路径时使用。
Webhook 可以按设计匿名接收；匿名入口或无签名 ping 被接受不自动证明漏洞。
核心是未经允许的事件是否改变受保护订单、账本或权益。

## 前提与隔离

只在提供商 TEST 模式、授权沙箱、自有测试订单和受控账号验证。
固定提供商、API/SDK、签名方式、商户/环境、端点及服务版本。
确认签名秘密的授权使用和存放方式，不传输到未批准外部服务。
实际资金、其他客户订单和不可恢复履约行为停止，不能用最小金额绕过范围。

## 数据与验证顺序

保留 raw body 原始字节，区分签名字节与解析后/重新序列化正文。
记录 header、算法、时间戳、签名版本、事件 ID 和密钥选择。
按提供商契约验证，不能泛化为所有提供商都采用同一 HMAC。
通常在产生业务效果前完成真实性、时间窗、环境/商户、事件与订单归属检查。
解析用于读取签名结构可能合理，重点是未验证数据不能触发业务副作用。
签名有效不代表金额、币种、收款主体和状态语义正确。
提供商回查或其他可信绑定方式按契约检查，不能仅相信 body 中的 paid 字段。

## 最小基线与单变量对照

1. 正常有效测试事件处理后，订单状态按预期改变且只改变一次。
2. 无/错误签名：回查是否真正丢弃，而非只看返回 200。
3. 错误密钥或错误环境：核查秘密选择与商户绑定，不借用他人凭据。
4. raw/parsed body 差异：只变一处语义，记录签名和实际处理正文。
5. 过期时间戳与原事件重放：核查时间窗与持久化幂等，分别解释根因。
6. 合法签名事件的订单、金额、币种、事件类型与环境归属。
7. 异步/部分失败：500 也可能已经提交，等待正常窗口后读回。
不同签名失败表现不能按每项各记一个漏洞；按根因和独立边界去重。

## 目标侧证据

保留请求、raw body 哈希/受控原件、响应、时间及执行关联。
测试事件 ID 使用可归因的无敏感 nonce，关联到自有订单。
正常认证路径读回订单、账本/权益和审核状态。
证明有效支付/批准行为缺失时，受保护状态仍被未授权改变。
如果只接收 ping、排队后拒绝、无状态改变，不能 confirmed。
只有真实新增权限/业务影响成立才提交完整 POC 和 validation。

## 反证与证明缺口

HTTP 200 可能为提供商重试策略而统一应答，不是接受支付。
签名样例通过只证明样例语义，不能证明目标密钥或验证链。
订单 read-back 不可用、异步尚未结束或提供商无法对齐时保留缺口。
有效秘密已经被其他漏洞取得，要声明该前提，不重复计正常持有者能力。
回调无需浏览器 CSRF 防护不等于认证绕过。
公开 client ID、demo 注释和测试密钥文案都不独立证明安全/不安全。

## 停止、清理与复测

缺 TEST 模式、自有订单、签名前提或恢复许可，记 blocked。
处理窗口有界且最多 5 分钟，等待期间继续独立 ready 单元。
非预期履约、账本异常或无法恢复立即停止，保存状态而不是继续发事件。
清理测试标记/订单时验收，保留必要支付审计。
复测原事件反例、正常有效事件、幂等、归属和共享消费者。

## 修复原则

使用提供商 SDK/方案校验确切字节和时间窗，拒绝跨环境/商户混用。
以可信订单绑定验证金额/币种/事件状态，必要时回查可信提供商状态。
持久化事件幂等并在事务/队列消费阶段统一执行。
日志脱敏，限制处理账号权限，失败关闭且正常业务保持。
