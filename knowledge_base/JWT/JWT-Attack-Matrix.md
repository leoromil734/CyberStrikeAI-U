# JWT 攻击矩阵（含绕过与验证）

> 上游 `README.md` 给出常见问题清单。本篇是**可执行矩阵**：每种攻击的前提、构造、验证证据与常见失败原因。

## 攻击矩阵

| # | 攻击 | 前提 | 构造要点 | 证据 |
|---|---|---|---|---|
| 1 | `alg: none` | 库接受 none 或大小写变体 | `{"alg":"none"}` / `"None"` / `"nOnE"`，去掉签名段 | 用伪造 token 访问受保护接口成功 |
| 2 | 算法混淆 RS→HS | 服务端用同一密钥做 RS256 校验但允许 HS256 | 用**公钥**作为 HMAC 密钥签名 | 接口以 admin 身份响应 |
| 3 | 弱 HMAC 密钥 | HS256 且密钥弱 | `hashcat -m 16500` / `jwt_tool` 字典爆破 | 还原出密钥并可重签任意 claims |
| 4 | `kid` 注入 | `kid` 进入文件路径/SQL | 路径穿越 `../../dev/null`（空密钥）、SQLi、命令注入 | 用已知密钥签名通过校验 |
| 5 | `jku`/`x5u` 劫持 | 服务端拉取 header 中的 URL | 指向自控 JWKS，内含自己的公钥 | 自签 token 被接受 |
| 6 | 内嵌 JWK | 服务端信任 header 里的 `jwk` | 自带公钥并自签 | 同上 |
| 7 | 声明绕过 | 校验逻辑缺陷 | `exp` 缺失/超长、`nbf` 未来、`aud`/`iss` 不校验、类型混淆 `"role":["admin"]`、`sub` 重复键 | 越权成功 |
| 8 | 密钥推导 | 密钥由已知值派生（时间戳、应用名） | 猜测并验证签名 | 可离线重签 |
| 9 | 重放/无撤销 | 无 jti 黑名单 | 登出后 token 仍有效；密码修改后旧 token 有效 | 会话固定/接管证据 |
| 10 | 签名剥离 | 中间件只解码不校验 | 修改 payload 后保持签名段 | 越权成功 |

## 常见实现细节坑

- 大小写与空白：`Bearer` 前缀处理、`type` 混淆（`typ:"JWT"` vs `"at+jwt"`）。
- 双 header：JSON 重复键，解析器取首/末不同（Go 的 `encoding/json` 大小写不敏感匹配 + 后者覆盖，2025 Trail of Bits 研究）。
- 空签名段：`header.payload.` 被部分库视为有效。
- 嵌套 JWT（JWE→JWS，或 `cty` 嵌套）：内层 claims 未校验。
- 时钟偏移过大导致 `exp` 校验被禁用。

## 验证流程

1. 抓取真实 token（登录/刷新接口）。
2. 本地解码 header/payload，确认 `alg`、`kid`、`jku`、有效期。
3. 逐个断言点做**单变量**修改，先证明服务端确实在解析该字段（改一个字符看是否报错）。
4. 仅当接口以**受害身份**返回数据或允许操作时，记为漏洞；仅有"可用于伪造的密钥"记为高危但需说明影响。
5. 记录 before/after 两段 token 与两次响应。

## 常见误报

- 篡改 token 后接口返回 401/403 → 说明校验存在，不要因为"能解码"就报漏洞。
- 前端把 token 存在 localStorage → 是风险点，不是 JWT 漏洞本身。
- 自建测试环境密钥弱 → 先确认生产同配置。
- 仅"无过期时间"但服务端有会话绑定。

## 修复

- 固定算法并显式指定（服务端校验 `alg` 白名单），禁用 none。
- HS/RS 密钥分离；HMAC 密钥 ≥ 256bit 随机。
- 不信任 header 中的 `jku`/`jwk`/`x5u`；`kid` 走白名单映射而非路径拼接。
- 强制校验 `iss`/`aud`/`exp`/`nbf`，并实现 `jti` 撤销与密钥轮换。
- 关键操作使用短期 token + 服务器侧会话绑定。
