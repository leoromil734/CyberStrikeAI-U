# 0day 与变体研究（从 N-day 到新漏洞）

> 目标：在授权范围内，用**可复用的方法**从已知漏洞出发找到新变体，而不是依赖单个 CVE。核心动作是"补丁对比 → 假设 → 最小 PoC"。

## 一、起点选择

| 起点 | 做法 |
|---|---|
| 补丁差异（Patch Diffing） | 拉取修复前后的代码/二进制，对比函数变化，找出"未修全"的分支 |
| 漏洞公告与演讲 | 从 Technique（技术）而非 CVE 出发，寻找同类组件 |
| 组件指纹 | 大范围识别同一库/框架的版本（同源组件常共享同类缺陷） |
| 不变量破坏 | 定义"必须成立的安全属性"，寻找违反它的输入 |
| 协议/规范歧义 | 规范允许的多种解释 → 实现之间产生差异（见 `../WAF-Bypass/Parser-Confusion-Bypass.md`） |

## 二、补丁对比流程（最有效）

1. **锁定版本边界**：安全公告与 CHANGELOG 找"修复版本"，下载前后两个版本。
2. **代码对比**：`git diff v1.2.3..v1.2.4`（或反编译二进制对比：`bindiff`/`diaphora`）。
3. **读补丁**：新增的检查是什么？它假设了什么？**这个假设能否被绕过**（编码、别名、并发、解析差异）？
4. **变体假设**：把检查逻辑抽象成规则，找出规则未覆盖的等价输入。
   - 关键字黑名单 → 等价语法（注释、编码、Unicode）
   - 路径检查 → 路径规范化差异
   - 类型检查 → 类型混淆/隐式转换
   - 单次检查 → TOCTOU/并发
5. **构造最小 PoC**：在本地/测试环境验证，逐步减小 payload 直至最小可复现。

## 三、黑盒发现方法

- **差分模糊测试**：同一输入发给两个实现（如两个代理、两个解析器），比较行为差异（对 HTTP 层极有效）。
- **协议模糊**：对状态机发送乱序/重复/边界消息；关注"错误路径"。
- **配置空间扫描**：同一产品不同默认配置下的行为差异（很多漏洞只在特定配置下成立）。
- **启发式 checklist**：把已知漏洞成因做成问题清单（例如"是否有地方解析用户输入两次？""是否存在两套权限判断？"）。
- **AI 辅助**：让模型在已知漏洞模式上生成变体假设，但**必须人验证**（模型的"漏洞"多为幻觉）。

## 四、判定与验证纪律

1. **可复现**：给出最小脚本与完整环境（版本、配置、请求序列）。
2. **可解释**：能说明根因（哪一行、哪个假设被打破）。
3. **影响可证**：证明实际效果（执行、越权、数据读取），而不只是"理论可行"。
4. **不夸大**：区分"崩溃/DoS"、"绕过校验"、"RCE"。
5. **负结果同样有价值**：记录"哪些变体不成立以及为什么"，避免重复劳动。

## 五、常见误报（研究场景）

- 不同版本行为差异被当成漏洞（其实是版本特性）。
- 只在自定义/调试配置下成立（生产默认不可达）。
- 需要竞争对手无法满足的前置条件（如本地管理员）。
- 触发崩溃但不可控（无利用价值）。
- 模型生成的"漏洞"无法构造 PoC。

## 六、伦理与边界

- 只对**授权范围内**的目标做研究；测试环境优先。
- 遵循协调披露（vendor 90 天常见窗口），发现即报告，不公开 PoC 直到修复。
- 不扫描/攻击互联网上未授权的同类产品（即使只是"指纹识别"也可能越界）。

